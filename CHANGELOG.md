### Added
- **[Ops]** The email send gate and the read guard for the claim signing key are registered in the main agent's hook configuration. Both run on every tool call (the send gate decides itself which calls are mail) under an 8 second deadline (`perl alarm`); a gate that runs out of time refuses. A crash or an unexpected exit code of either hook counts as a refusal, and a refusal (exit 2) stays a refusal: the registration does not use `timeout`, which macOS does not ship.

- **[API]** An `email_send` approval request is now bound to one exact mail. `POST /api/approvals` for `email_send` takes the JSON envelope of the mail as `action_payload` (`to`, `cc`, `bcc` as bare addresses, `subject`, `body`, optionally `html_sha256`, `attachments`, `from`, `reply_to`, `in_reply_to`), builds its canonical form, stores the sha256 of that as `content_hash`, and writes `action_description` itself from the envelope, so what the person deciding reads is provably what is hashed; the requester's own description is ignored. A `content_hash` the client sends must match the server's (`400`, `code` `hash_mismatch`). Only the main agent can open an `email_send` request: a sub-agent gets `403`, as does any spelling of the name that imitates it. Asking again for the same mail while its request is open returns that request (`200`, `deduplicated: true`) and tells nobody; an agent can have 10 open requests (`409`, `reason` `too_many_pending`) and the owner is told of at most 5 new ones per agent and hour. `GET /api/approvals` takes an exact `content_hash` filter, and `GET /api/autonomy` carries `approvalHumanOnlyEnforce`, whether the human-only rule binds on this server. Behaviour change: an `email_send` request without an envelope, or from a sub-agent, is no longer accepted. The golden vectors that fix the canonical form for the server and the send gate are in `scripts/__tests__/email-envelope-vectors.json`.
- **[API]** The storage layer for a hash-bound approval (the two routes of the next entry use it). `consumeApproval` uses an approval up by id and `claimApproval` by the hash of the action: either succeeds only for an approved, unconsumed `email_send` row of the same tenant and the same agent, bound to exactly that hash, decided by a person's dashboard session no longer ago than the window, and it is one guarded write, so of two callers racing for a row exactly one wins. A retry with the same ref inside 60 s answers as a replay instead of burning a second approval. A refusal says why (`not_found`, `agent_mismatch`, `wrong_category`, `already_consumed`, `not_approved`, `hash_mismatch`, `expired`, `not_human_decided`; a claim also `pending`, `none`, `rejected`) and is journalled in `approval_events`. `createApprovalOnce` opens a request unless the same one is already open or the agent is at its cap of open requests, in one transaction. The approvals list takes an exact `content_hash` filter. All three refuse a hash that is not 64 lowercase hex characters (`hash_mismatch`) before they read or write a row. No new migration: 0080 and 0081 already carry the columns and the index.
- **[API]** An approved `email_send` request can now be used up, once. `POST /api/approvals/:id/consume` (body `content_hash`, optional `ref`, `consumer`) uses up the named request, and `POST /api/approvals/claim` (body `category`, `content_hash`, optional `ref`, `consumer`) finds the request for the mail with that hash and uses it up; both answer `200 {ok, replayed, window_s, approval}`. They are the send gate's calls and need the token of the agent that asked: a shared token, a dashboard session or another agent's token is `403` (`agent_identity_required` / `agent_mismatch`), another tenant's request is `404`. A refusal is `409 conflict` with a `reason` (`already_consumed`, `not_approved`, `hash_mismatch`, `expired`, `not_human_decided`, `wrong_category`; a claim also `pending` with the open request's `approval_id`, `rejected`, `none`) and the state of the row, never its content; every call, refused or not, leaves an `approval_events` row and an audit entry. New permission `approvals:consume`, held by `admin` and `fleet_agent` only (a `read_only` or `viewer` user, who can approve, cannot use an approval up). `APPROVAL_CONSUME_WINDOW_S` sets how long after a person's decision the mail may still be sent with it: default 1800, a value outside 60..86400 is pulled to the nearest bound, anything not a whole number is the default. `GET /api/approvals/:id/events` lists the journal of one request for the owner and tenant users (tenant-scoped, `403` for a fleet agent token).
- **[API]** The `200` answer of `POST /api/approvals/claim` and `POST /api/approvals/:id/consume` is now signed: `sig` is the HMAC-SHA256 (lowercase hex) of `v1|content_hash|category|agent_id|ref|consumed_at`, built from the stored `approval` row, so a replay carries the same `sig`. The key is the 32 random bytes the file `store/.claim-signing-key` holds as 64 hex characters: the dashboard creates it (mode 0600, only when missing, never logged, never returned by a route) at startup. A key that cannot be read or is not a key makes both routes answer `503` (`internal_error`, `reason` `claim_signing_unavailable`) BEFORE anything is used up, never an unsigned `200`. A listener on the dashboard's port that only mirrors the request can echo the hash and the reference but cannot sign. `docs/openapi.yaml` and the SDK carry `sig` (required in `ApprovalUsed`) and the `503`.
- **[Ops]** `scripts/gmail-send.py` is the official plain-text mail sender, with the approval claim on the sender side. It reads its command line (`--to`/`--cc`/`--bcc` repeated, `--subject`, `--body`, `--body-file` or stdin, `--attach`, `--from`, `--reply-to`, `--in-reply-to`) through the send gate's reader (`gmail_send_fields` in `scripts/lib/email_extract.py`), so the hash it claims is the hash the gate computes for the same command line. It refreshes the Gmail login first (a broken login burns no approval), then spends the owner's approval for that hash with the main agent's own token (`POST /api/approvals/claim`, the answer checked field by field; the shared-token fallback, a `WEB_HOST` that is a name, a proxy and a redirect are refused), re-reads every attachment and refuses one that changed after the hash, and sends exactly the approved fields through the Gmail REST API. With no usable approval it opens a request and exits `3`; the same command is run again after the owner decides. No flag or variable skips the claim, and there is no `--html` in this version (the owner approves the text, so the text is what is sent). `GMAIL_CRED_DIR` and `GMAIL_SEND_API_BASE` (test seams) and `GMAIL_SEND_DRY_RUN=1` (prints the hash, calls nothing) are documented in the script. Limits: an agent can still write its own script, and the other send routes (`send.py`, `graph-mail`, `send-digest-email.py`) are not converted yet.
- **[Ops]** `scripts/approval-consume.py` uses up an approved `email_send` request from the command line: `--hash <sha256>` claims by the hash of the mail (`POST /api/v1/approvals/claim`), `--hash <sha256> --id <approval id>` consumes that approval, `--ref` and `--consumer` label the use for the journal. It authenticates with the calling agent's own token (never a command-line argument, never printed; the shared dashboard token is not read) and talks to the dashboard over HTTP only. Exit codes: `0` only for HTTP 200, `3` for a refusal (403 or 409, the reason on stderr), `4` for an unknown id (404), `2` for anything else (network, 400, 5xx, no token, bad arguments).
- **[API]** `docs/openapi.yaml` and the generated SDK describe the approval use-up routes: `POST /approvals/claim`, `POST /approvals/{id}/consume` and `GET /approvals/{id}/events`, the `409` `reason` values, the `403` `agent_identity_required` and `agent_mismatch` answers, the `consumed_at`, `consumed_by` and `consumed_ref` fields of `Approval`, and the `deduplicated` `200` of `POST /approvals`. Documentation only for the routes already listed above; no behaviour change.
- **[Ops]** Documentation of the email approval: the user guide (`03-approvals`, English and Hungarian) explains it from the owner's side, `SECURITY.md` and the fork guide F02 state what it protects and what it does not, including that an `email_send` approval request can only be opened by the main agent (a sub-agent gets `403`), and F02 documents `APPROVAL_CONSUME_WINDOW_S` (default 1800 seconds, pulled into 60 to 86400, a value that is not a whole number is the default). The send gate that would stop the mail-sending tools without an approval, and the official sender, are planned and not installed; the documents say so and do not call this a real gate yet.
- **[UI]** The Approvals detail shows an `email_send` request as the mail it binds: recipients (to, cc, bcc; an empty cc or bcc reads "(none)") one per line, the subject, the whole body in a scrollable box, the attachment names with their sha256, and a fingerprint of the content hash (first 12 hex, the full hash in the tooltip). The agent-written fields are escaped and shown as text, never as markup. Markers beside the status say whether the mail was used up (when, by whom) or is approved and not used yet, whether the request expired undecided, and whether a person (dashboard session) or a token (advisory) decided it; the list carries the used-up and not-used-yet markers and cuts the server-built description to 80 characters by code point. The detail also reads `GET /api/approvals/:id/events` and lists the journal oldest first (used up, use refused with its reason, token decision on a human-only request, owner not reached, duplicate request folded in, notification suppressed) with labels in Hungarian and English; a login that may not read the journal sees a note instead. The detail labels, the row hint and the modal title are translated now. The page does not show how long an approval can still be used: that window (`APPROVAL_CONSUME_WINDOW_S`) is not in the list answer, so an approved mail whose window has passed reads "approved, not used yet" until a refused use appears in the timeline as "approval window passed".
- **[API]** `GET /api/approvals` now carries the length of the use window as `window_s` (seconds, `APPROVAL_CONSUME_WINDOW_S`), on every page and for every kind of caller. The Approvals list and detail use it: an approved `email_send` request that nobody used up and that was decided longer ago than the window gets the marker "Expired (window)" ("Lejárt (ablak)") instead of "Approved, not used yet", because the server no longer lets it be used. A server that does not send the field leaves the old marker. `docs/openapi.yaml` also describes the real shape of the list answer (`ApprovalList`: `items`, `total`, `offset`, `limit`, `counts`, `oldest_pending`, `window_s`), which it had given as a bare array, and the generated SDK follows.
- **[Ops]** The email send gate has its reader: `scripts/lib/email_extract.py` turns an outgoing mail call into the canonical envelope and the sha256 the dashboard computes for it (`build_envelope`, a mirror of the server's `parseEmailEnvelope`) and reads the mail out of every shape a call can have (`collect_email_envelope`): an MCP mail tool input, `send.py`, `graph-mail send`, `gmail-send.py`, `sendmail`/`msmtp` with a raw message on stdin, `mail`, and `curl` to the Gmail send route (a base64url raw message) or the Resend API. It fails closed: a shell expansion in a word it needs, a pipe as the body, a second mail in the same call, a duplicated Subject or From header, an `@` that no parsed address accounts for, a line break in the subject, an unknown option or a file it cannot read make the call unreadable, with the reason. The contract is `scripts/__tests__/email-envelope-vectors.json`, now with an `extract` section (calls with the hash the server computes for the mail they carry, and calls that must be refused); the server tests check the stored hashes and `scripts/__tests__/email-extract.test.py` checks the reader against all of it. Nothing calls the reader yet.
- **[Ops]** The email send gate itself, `scripts/hooks/email-approval-gate.py` (PreToolUse, for the main agent): a call that sends a mail needs one approval bound to that exact mail. It runs the copy gate first, in the same process, and takes its verdict as it is; then, for a mail call, reads `email_send` from `GET /api/autonomy` (level 1 and anything that is not a clamped 2 refuse, and so does a server that does not enforce human-only decisions), reads the mail out of the call (an unreadable mail refuses and says how to make it readable) and spends an approval with `POST /api/approvals/claim` under the main agent's own token; with none to spend it opens a request for the owner and refuses with the request id, so the same mail can be sent again once the owner has decided. A dashboard that does not answer, a slow or odd answer, a part that does not load, a missing own token: all refuse, with the reason; there is no shadow mode and no switch. The dashboard address is `WEB_PORT` from the install's `.env`, never the agent's environment, with no proxy and no redirect. Every verdict about a mail call is one line in `store/email-approval-gate.log` (the hash prefix, the number of recipients, the level, the reason; never the mail). `scripts/__tests__/email-approval-gate.test.py` runs it against a stub dashboard. It is not registered yet (the owner adds the PreToolUse entry for it to the root hook configuration and restarts the session), and the official sender and the other send routes (a Gmail REST call from a script) are still not covered, so this is not yet a closed gate.
- **[Ops]** `store/.claim-signing-key` is a new secret of the store (the key of the claim signature above). `store-watcher` treats it like the other secret files of the store: no audit row for its creation. It is read by the send gate and by `scripts/gmail-send.py` from their own install path, and only the server writes it.
- **[Ops]** The email send gate now sees a curl to a mail API as a send. `command_sends_mail` in `scripts/lib/email_extract.py` judges by text, fail closed: a command that runs curl and has any word naming `gmail.googleapis.com`, `www.googleapis.com` or `api.resend.com` (also inside a quoted or dynamic URL, `--url X`, a `U=https://...` assignment or a shell `-c` code) is a send, so it needs the same approval as any mail tool, and a URL or body the reader cannot read is refused. A curl to any other host is not a send. Behind a pass-through wrapper (`env`, `command`, `exec`, `nohup`) the "only looks at files" shortcut is no longer applied (`env -u cat timeout 5 send.py` was read as `cat`). A curl to the Drive or Calendar API on `www.googleapis.com` is a possible send as well and is refused as unreadable: the false alarm is the safe side.
- **[API]** `POST /api/approvals` for `email_send` now refuses a mail with an HTML part (`html_sha256` in the envelope) with `400`, `code` `html_not_supported`: the person deciding is shown the text part and a fingerprint of the HTML, the recipient reads the HTML, so harmless text could be approved and another page sent. The send gate (`scripts/hooks/email-approval-gate.py`) refuses such a mail too, before it asks for or spends an approval, and says to send plain text. A mail with an HTML part can be approved again when the dashboard shows that part as text.
- **[Ops]** The mail reader and the send gate close more ways round them: a `curl` URL or `-T` file with a glob (`{a,b}`, `[1-3]`) is unreadable unless `--globoff` and a quoted word are given (curl would send one mail per expansion with one approval); a mail program named behind a wrapper the classifiers do not follow (`timeout`, `nice`, `sudo`, `xargs`, `stdbuf`, `eval`, `find -exec`, `watch`, `ssh`, `bash -lc`), in an assignment before the command, in a git config value, or by a command whose own name is a variable, counts as a possible send and is refused as unreadable; and without the reader the gate refuses a Bash call instead of guessing from a name list of its own. A command that names a mail program is a possible send unless its program is a plain file viewer or copier (`cat`, `ls`, `grep`, `cp` ...): `git` and `rg` are not trusted, because an option or a subcommand can make them run it. A wrapper (`eval`, `xargs`, `timeout`, `sudo`, `find`, `ssh` ...) or an interpreter `-c` / `-e` given a variable to run is refused as a possible send.
- **[Ops]** The send gate asks the dashboard at its IP address (`WEB_HOST` from the install's `.env` when that is an IP address, otherwise `127.0.0.1`), not at the name `localhost`, which can resolve to `::1` where a listener started by the agent could answer in its place; and it accepts a `200` from the claim route only when the approval in the answer names this mail's hash, `email_send`, this agent, the status approved, and this use (the reference the gate made up for the call). A signed answer is left for a later version.
- **[Ops]** The send gate and `scripts/gmail-send.py` now check the signature of the approval answer. They recompute `sig` (HMAC-SHA256 of `v1|hash|category|agent_id|ref|consumed_at`) with the key in `store/.claim-signing-key`, read from their own install path, and refuse an answer with a missing or wrong `sig`, a missing or malformed key or a missing `consumed_at` (code `claim_unsigned`). A listener that only mirrors the request, and so passes the echo check, no longer passes for the dashboard.
- **[Ops]** `scripts/hooks/secret-read-gate.py` is a PreToolUse read guard for `store/.claim-signing-key`: it refuses a call of ANY tool (Read, Edit, Write, Grep, Glob, Bash, the MCP file tools such as `mcp__filesystem__read_text_file`, `write_file`, `move_file`, and tools that do not exist yet: every string of the arguments is judged, nested lists and objects included) that would read or change the key (the name in its spellings, globs including bash's `^` negation and POSIX classes, paths that resolve to it through links, recursive readers over the store directory). A text and real-path denylist, fail-closed, no switch; the owner registers it in the root hook configuration with a matcher that covers every tool, this change does not.
- **[Ops]** `scripts/gmail-send.py` takes `GMAIL_CRED_DIR` and `GMAIL_SEND_API_BASE` from the install's `.env` only, not from the environment, and the default credential directory from the account, not `$HOME`. The token endpoint of the Gmail login must be https on a Google host (or, with a stand-in base named in `.env`, the same origin as it), and the Google calls use their own opener: no proxy, no redirect, certificates checked against the CA paths compiled into Python, not `SSL_CERT_FILE` / `SSL_CERT_DIR`.
- **[Ops]** The email-approval texts in `SECURITY.md` and the fork guide (F02, English and Hungarian) now say what exists (send gate, official sender, signed answers, read guard) and what still keeps it from being a real gate: the hooks are not registered by the repository, the command classifier is best-effort, and the key is readable by the agent's operating-system user.
- **[Ops]** `RBAC_MODE` now defaults to `enforce` when it is not set: the RBAC gate refuses what a role does not allow out of the box. Shadow mode (log only, nothing blocked) has to be asked for by name with `RBAC_MODE=shadow` in the process environment or `.env`; any other value, an empty one or a misspelling included, is `enforce`, so a typo can no longer switch the gate off. An install that already sets `RBAC_MODE=enforce` sees no change. An install with no setting that relied on the old shadow default starts refusing what a role does not allow after the next restart; check the shadow log (`rbac_shadow_log`, `GET /api/v1/rbac/shadow-log?summary=1`) for `would-deny` rows first, and set `RBAC_MODE=shadow` to roll back.
- **[Ops]** New PreToolUse gate `scripts/hooks/auth-admin-gate.py`: an agent's Bash may not run the dashboard-user CLI (except the read-only `list`) or `security-reset*`, may not pass `--password-stdin`, and may not write the auth tables (dashboard_users, auth_sessions, api_tokens, device_keys, approvals, approval_events) of the live store with sqlite3, python or node. Reads, copies of the database elsewhere and a CLI run with `MARVEEN_STORE_DIR` set to a throw-away store are untouched. Bounded and fail-closed. Any other command whose argument resolves to the live database file (by name, inode, hardlink or symlink) is refused unless it is a known reader. Good-faith protection against the same OS user, like the docs say: it is a denylist, and writes to the schema table (`sqlite_master`, `PRAGMA writable_schema`) are refused too. Known limits remain: a python/node script FILE is not read (only `-c`/`-e` code), names built at runtime in code (string concatenation, `getattr`) are not seen, a shell function wrapping a writer, an interpreter given the live file as an argument, archive contents and extraction into the store's parent directory, some sed `w` and curl/wget output forms (`--output-dir`, `--config`), a long CREATE TRIGGER header, and sqlite3 `.load`. Wired like the destructive gate (Bash matcher, timeout 10, fail-closed `command -v python3` guard): in the tracked project `.claude/settings.json`, in `templates/settings.json.template`, into every new sub-agent's settings, and backfilled into existing sub-agents on dashboard startup (`ensureAuthAdminGate`). A running agent picks it up on its next restart.
- **[UI]** The kanban board shows a card's priority on the whole card instead of a 3 px stripe: urgent and high cards get a tinted fill and edge (stronger in the dark theme), normal and low stay plain, and a stale card keeps its aging stripe. Beside the view switcher the board now reads "{open} open / {all} on the board" (open = every card not in Done), with "({n} shown)" added while a project, assignee or label filter narrows it. The totals and the column counters come from the server's per-status totals when the board is paged, so a column with 25 cards reads 25 while 20 are loaded (the WIP badge used the loaded count too and is corrected); they are tenant-scoped like the list itself. Port of the upstream card tone and board totals, adapted to the paged board.
- **[Ops]** Three more scripts find the dashboard port instead of assuming 3420, so an install on another `WEB_PORT` is no longer talked past: the fleet memory-heartbeat sweep (`scripts/fleet-heartbeat-sweep.sh`) leaves it to `scripts/agent-api.sh`, and `scripts/blackboard-hygiene.py` and the `fleet-helper` seed skill (`fleet.py`) read `MARVEEN_WEB_PORT`, then `WEB_PORT`, then `WEB_PORT` in the install's `.env`, then 3420, the same order as `agent-api.sh`. An explicit `MARVEEN_DASHBOARD_BASE` (hygiene) or `CLAW_BASE` (fleet-helper) still wins. With no setting nothing changes. The seed skill reaches a running install through the skills table, not by the seed file alone. Port of the upstream port-literal cleanup; the hook scripts that still carry the literal are handled separately.
- **[UI]** The kanban board can order the cards of each column: a Sort selector next to Group by offers manual order (the default, the drag order), by number ascending or descending, by created and by updated (newest first); a card with no number or time goes last, ties keep the manual order, and the choice is remembered in the browser. Outside the manual order cards cannot be dragged and the whole board is loaded instead of page by page (a partial page would sort wrongly); the swimlane view uses the same order. New Ongoing band: an open card labelled `Folyamatos` or `Ongoing` (case-insensitive, per tenant, the name list is one array in `web/modules/kanban-ongoing.js`) leaves its status column for a band of buttons above the board, keeps its status, is not a drop target, and returns to the Done column when done; its subtasks stay in their own columns. While the tenant has such a label the board is loaded in full so the band is complete. A banded card is left out of the column header number and the WIP badge (it is in no column) and stays in the board total; the column count is built from the cards the column renders (`kanbanColumnGroups` in `web/modules/kanban-totals.js`), and because a label forces the full load, the paged server-total path never holds an unloaded banded card. Search is unchanged (the existing server-side search). Port of the upstream column sort and ongoing band, adapted to the paged board.
- **[API]** The approval flow's own notices (`[APPROVAL_REQUEST]`, `[APPROVAL_REQUEST][HUMAN_ONLY]`, `[OWNER_UNREACHED]`, `[APPROVAL_RESOLVED]`) are now server-only markers: `POST /api/messages`, `PUT /api/messages/:id` (its `result`, which is echoed back to the sender) and `POST /api/federation/inbox` refuse any text whose first line (full-width, look-alike-letter, invisible-character, leading-whitespace, leading-Markdown-emphasis/heading, Markdown backslash-escaped, HTML-character-reference, percent-encoded-bracket and leading-inline-HTML-tag (`<b>`, `<span ...>`, `<p>`, a link; `<code>` and `<pre>` stay quotation) forms included) opens with one of them, with `400` `invalid_value` and `code` `reserved_marker`, unless the sender is the server's own `system`; claiming to be `system` itself is a separate `403` `forbidden` with `code` `reserved_sender`, whatever directory or `SYSTEM_SENDER_IDS` entry matches that name. A marker mentioned mid-line, quoted or in a list item is untouched. The same check is the database layer's own choke point (`createAgentMessage`, the tenant-scoped insert), so no writer can bypass it by skipping the HTTP route. Closes the gap where any agent could put a request or an outcome in front of another agent's inbox and have it read as the server's own word on a pending or decided approval. Known limit, on the safe side: a marker on a line of its own inside a Markdown code fence is refused too (the filter does not track fences), so quote it mid-line instead.
- **[Ops]** The main agent's `approval-request-handling` skill (seed) knows the human-only approval flow. A request marked `[APPROVAL_REQUEST][HUMAN_ONLY]` is not forwarded to the owner and not PATCHed (the server already told the owner, with a dashboard link, and refuses a token with `403 human_only_category`); a typed "IGEN <id>" in the chat is not an approval; `[OWNER_UNREACHED]` means "tell the owner on your own channel, ask for no reply"; `[APPROVAL_RESOLVED]` is a hint, not the decision (any agent can send text that looks like it): the requester reads `GET /api/approvals/<id>` and acts only when the server answers `status=approved` with `resolved_via=dashboard_session` (`rejected` and `timeout` never run the action). The marker decides, not the category name: a request without it (enforcement still off) follows the traditional relay chapter, which is kept, and a `403 human_only_category` there sends the agent to the human-only chapter. A contract test ties the skill to the message lines the server builds. The skill reaches a running install through the skills table, not by the seed file alone.
- **[Ops]** `npm run dashboard-user -- list` prints each login's role and tenant (`person-a  role=admin  tenant=global  created ...`, a login without a tenant is `tenant=global`), so the owner can confirm from the machine that a login is a global admin, the only kind that decides a human-only approval, without opening the dashboard. The line format moved to `scripts/lib/dashboard-user-format.ts`; a password or its hash is never printed.
- **[API]** What an agent writes into an approval request no longer reaches the main agent as raw text. The inter-agent lines for a request (`[APPROVAL_REQUEST]`, `[APPROVAL_REQUEST][HUMAN_ONLY]`, `[OWNER_UNREACHED]`) now carry the requester's id, the category and the action as quoted data: flattened to one line, without control or invisible characters and backticks, inside a code span, cut to 64 characters (id, category) and 1000 (action) with a marked cut. A newline, a backtick or a forged `[APPROVAL_RESOLVED] ... status=approved` in an action can no longer start a notice of its own or pose as one of the line's fields. This applies with `APPROVAL_HUMAN_ONLY_ENFORCE` on or off (it only hardens what the main agent reads; nothing that was allowed is refused). The line now reads `agent=\`agent-b\` category=\`email_send\` action=\`...\``.
- **[Ops]** `scripts/workspace-put.py` accepts `series-<slug>/<part>` doc keys, so every part of a multi-part work (for example an article series) can live under one prefix next to the existing `plan`, `brief`, `report`, `notes` and `draft` ones. The `series-` prefix implies no document type: `--type` takes any of the four and defaults to `notes`; the other prefixes keep their implied type and still refuse a different `--type`. The slug is lowercase letters, digits, `_` and `-`, starting with a letter or digit; the 2-4 segment limit, the character set and the 200-character cap are unchanged. The key check also stops accepting a trailing newline (`$` matched before it), so a control character can no longer reach the store through a key.
