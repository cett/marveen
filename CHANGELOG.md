### Added

- `scripts/hooks/context-watchdog.py`'s HANDOFF injection now dedups instead of firing on nearly every PostToolUse call once context crosses 60% (previously ~every call, several hundred over a 60->100% run): `should_emit_handoff()` reads the session's own prior `verdict='handoff'` row back out of `hook_audit_log` (no new persistent state) and only actually emits on a first crossing, a pct-band change (60/70/80/90, with 95%+ as its own band), a >=5-point same-band pct drop (compact/reset detection), or a real content change once enough time has passed (300s, 60s once pct>=90%) -- expected to cut emits from ~hundreds to ~6-15 per run. `hook_audit_log.content_hash` (column already existed, previously always empty for these rows) now carries an 8-hex sha1 of the HANDOFF body with its two always-changing lines (the header timestamp, the token-count line) stripped, so a real content change can be distinguished from clock/token drift. A dedup-query failure fails open (emits) -- this stays a logging-category hook that never blocks the tool call. QA follow-up: mutation testing found the dedup gate's decision logic well-covered but 2 real gaps -- no test exercised the query's `ORDER BY ts DESC, id DESC` tie-break against 2+ real rows (only pure-function tests existed, all with a single seeded row), and no test drove the gate through `main()`'s actual subprocess path across several real calls. Both closed: a new `TestMainSubprocess` case runs 5 real hook invocations in one session (60/61/62% -> 1 emit, 70% -> 2nd emit, 71% -> skip) and asserts exactly 2 audit rows, which only holds with a correct newest-row tie-break once ties are broken by row id; plus standalone tests for an identical-hash skip surviving a long time gap, a different agent_id under the same session_id never deduping against another agent's row, an unparseable prior `reason` failing open, and `main()` actually persisting `content_hash` into the audit row. A leftover dead `try`/`except` in `should_emit_handoff()` (the wrapped call already fails safe on its own) was also removed -- no behavior change.
- Config/state -> SQLite migration post-audit: dangling references to the JSON side-cars already migrated into SQLite by earlier groups, found and cleaned up. `context-watchdog.py`'s `_read_gate_threshold()` read the retired `store/context-restart-gate.json` directly (a stale copy no write path kept in sync) -- it now reads the `agent_settings` row (`setting_key='context_restart_gate'`, migration 0058) the actual gate reads, with a new unit-test class and its own Python-side test-fixture DB table. `migrateGroup5StateFromFiles()` (group 5/8) backfilled `model-fallback.json`/`agents-desired.json`/`terminal-input.json` into `system_config` but never retired them, unlike every sibling group -- new `retireGroup5StateFiles()` (mirroring `retireAgentSettingsFiles()`'s multi-file pattern) renames all three to `.deprecated` on real process boot, with unit tests. Docs/scripts touch-ups: `.env.example`'s federation note now points at the `system_config` row instead of the long-gone `store/federation.json`; `scripts/doctor.sh`'s `HEARTBEAT_AGENT_ENABLED` check now reads `system_config` (db-over-env, matching `cfg()`'s real precedence) before falling back to `.env`, instead of the retired `config-overrides.json`; `scripts/pre-modify-backup.sh` no longer copies the three retired group-3/5 side-cars (their state is already captured by the SQLite `.backup` above it); `scripts/hooks/egress-gate.mjs`'s block message now points at `POST /api/v1/egress-allowlist` instead of hand-editing `store/egress-allowlist.json` (that file itself is unchanged -- it remains the hook's offline fallback, only the suggested fix path changed).

- Schedules tick-status badge: a future-skew tick timestamp (`ageSeconds: null`, `lastTickMs` set -- clock jump/corrupted row) now renders its own "clock anomaly" warning message, distinct from the generic "no tick data" shown when there is truly no stamp yet (`lastTickMs` also null). - Federation peer config (peers, per-peer inbound/outbound tokens, routing mode, enabled flag) moved from `store/federation.json` to a `system_config` row (key `federation_config_json`), completing the piece group 5/8 deferred. Unlike `vault_bindings` (a normalized table), the whole document is kept as one raw JSON blob so the existing "lossless disable" contract keeps working unchanged: an invalid stored peer still round-trips byte-for-byte on a flag-flip write, which a normalized table could not hold at all. Fail-closed unchanged: any DB read/parse/validation error yields a disabled config with no peers, now logged via `logger.error` (was `logger.warn` for a merely garbage/invalid document -- a DB read failure is a different, more serious class of error and is now distinguished in the logs). Public API is unchanged: `getFederationConfig`/`writeFederationConfig`/`validateFederationConfig`/the federation routes all keep their exact signatures, only the storage underneath moved.
