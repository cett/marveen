### Added

- The nightly backup and the memory maintenance are now seeded as `type: command` scheduled tasks (no LLM, no prompt), so a fresh install gets them the way a long-running one already runs them: `nightly-backup` (`0 3 * * *`, runs `scripts/backup.sh`, 120 s timeout) and `memory-maintenance` (`15 3 * * *`, resorts the memory tiers and prunes versions, then maintains the link graph, 480 s timeout), both enabled and alerting on the first failure. The command is rendered with the install directory and dashboard port, so it carries no hardcoded path. `memory-maintenance` was seeded before as a disabled prompt task and its `SKILL.md` is gone from the seed; an existing install keeps whatever it has, because the schedules table is the source of truth and is only filled from the seed files while it is empty. Covered by a regression test that renders the seed the way the installer does and checks a fresh DB gets two command rows without a prompt while an existing row stays unchanged.
- `scripts/blackboard-hygiene.py`, a deterministic replacement for the LLM-driven blackboard-hygiene-monitor heartbeat, meant to run as a `type: command` scheduled task. It finds running agents whose tmux pane shows an active turn (spinner line or `esc to interrupt`) but whose Fleet Blackboard row is missing, `done`/`blocked` for more than 15 minutes, or older than 2 hours, nudges them over the inter-agent queue, and after two consecutive nudges without improvement sends one `[ESZKALACIO]` message to the coordinator (a command task has no chat tool of its own) and resets the counter. The consecutive-nudge counters stay in `agent_state`; the coordinator is taken from `MAIN_AGENT_ID` and is never nudged. `GET /api/blackboard` only lists the 10 freshest rows, so an agent whose row fell off that list is looked up via `/api/blackboard/history` before it counts as having no row. `--dry-run` decides and prints without sending or writing; a dashboard read failure or an undeliverable message exits non-zero so the command-task failure alerting can see a broken monitor. The schedule itself is switched to `type: command` separately.
- `scripts/tenant-gate-rollout-check.py`, a read-only report for rolling out the tenant skill gate: migrations 0064/0065 applied, hook scripts present, both hooks wired into every sub-agent in the current fail-closed form, the main agent not gated, live evidence per agent (`agent_tenant_context` rows) and multi-tenant agents that have no channel binding yet. `--strict` fails on warnings, `--json` for machines; nothing is written.
- Tenant skill files now follow the agent's process lifecycle instead of the dashboard's: they are generated when an agent STARTS (before its session launches, so the loader sees them) and the generated copies (SKILL.md and companion files) are deleted when it STOPS, DB -> cache being the only automatic direction. A hand-edited SKILL.md or script is kept at stop (its generated companions still go). The startup regen and live skill edits write tenant copies for running agents only and prune the generated copies of stopped ones, which also cleans up after a crash. `TENANT_SKILL_FILES=off|single|all` keeps its meaning.
- `scripts/hooks/tenant-skill-gate.py`, a PreToolUse gate that keeps a tenant's skills inside that tenant's requests: the `Skill` tool, and Read/Edit/Write/Glob/Grep/Bash calls that point into a tenant skill's directory (its companion scripts included), are blocked unless the active tenant (from `agent_tenant_context`) owns the skill or was granted it; fleet skills and everything else are never touched, and calls that cannot involve a skill directory do not open the database. Fail closed: no context, an unknown or conflicting tenant, a context older than `TENANT_CONTEXT_MAX_AGE_SECONDS` (default 12 h), an unreadable database or a gate error all block. The shell side is best effort (a command can build a path indirectly) and a search rooted above the skills directories is allowed. Not registered yet.
- A message an agent sends is now stamped with the tenant of the request that agent is serving (its `bound` `agent_tenant_context`), so a coordinator's delegation carries the tenant to the receiving agent. Anything else (no context, default, unknown, conflict, stale, the agent no longer serving the tenant, a lookup error) stays `default`, the least-privileged stamp; explicit partner-tenant sends and messages to federated recipients are untouched. The tenant context is also re-validated at use time: the prompt hook and the skill gate treat an agent as serving a tenant only while the tenant is not disabled and the agent is its main agent or enabled for it, and changing or deleting a channel binding, disabling an agent for a tenant, disabling a tenant or changing its main agent drops the affected agents' recorded context at once.
- The two tenant hooks (`tenant-context.py` on UserPromptSubmit, `tenant-skill-gate.py` on PreToolUse for `Skill|Read|Edit|Write|NotebookEdit|Glob|Grep|Bash`) are now registered into every sub-agent's `settings.json`: new agents get them at creation, existing ones by the idempotent startup backfill (`ensureTenantHooks`, next to the destructive gate), and a half-wired or stale-matcher entry is repaired. Both are fail-closed python3 commands (no interpreter blocks). The main agent is exempt here: its hooks are repo-shipped project settings.
- `agent_tenant_context` (migration 0065) and the `scripts/hooks/tenant-context.py` UserPromptSubmit hook: on every prompt an agent receives, the tenant of the request is resolved from the source (channel chat via `tenant_channel_bindings`, inter-agent message via its `agent_messages` row, scheduled task via its `schedules` row; nothing, i.e. the local operator, is the default tenant) and recorded as one row per agent. Only the top-level prompt structure is read, so a marker forged inside a chat or peer message body is never a source; an unidentifiable source is `unknown` and a batch mixing tenants is `conflict`, both meaning no tenant skills. If the row cannot be written the previous request's tenant is invalidated, and if even that fails the prompt is refused. Groundwork for use-time skill isolation; the hook is not registered yet and nothing reads the row yet.
- **[API]** `tenant_channel_bindings` (migration 0064): which tenant an incoming source (Telegram chat, dashboard chat, inter-agent sender) belongs to, per agent, so an agent shared by several tenants can tell whose request it is answering. New admin routes `GET`/`PUT`/`DELETE /api/admin/channel-bindings`; a source belongs to exactly one tenant, binding to a non-default tenant requires the agent to be enabled for it, and a source without a binding is the `default` tenant. Deleting a tenant removes its bindings. Groundwork for use-time tenant skill isolation; nothing reads the table yet.
- `scripts/hooks/context-watchdog.py`'s HANDOFF injection now dedups instead of firing on nearly every PostToolUse call once context crosses 60% (previously ~every call, several hundred over a 60->100% run): `should_emit_handoff()` reads the session's own prior `verdict='handoff'` row back out of `hook_audit_log` (no new persistent state) and only actually emits on a first crossing, a pct-band change (60/70/80/90, with 95%+ as its own band), a >=5-point same-band pct drop (compact/reset detection), or a real content change once enough time has passed (300s, 60s once pct>=90%) -- expected to cut emits from ~hundreds to ~6-15 per run. `hook_audit_log.content_hash` (column already existed, previously always empty for these rows) now carries an 8-hex sha1 of the HANDOFF body with its two always-changing lines (the header timestamp, the token-count line) stripped, so a real content change can be distinguished from clock/token drift. A dedup-query failure fails open (emits) -- this stays a logging-category hook that never blocks the tool call. - **[API]** `PUT /api/schedules/{name}` no longer writes whatever keys the body carries. - The scheduler no longer lets an enabled task's due occurrence disappear without a trace. The fire loop used to `continue` silently past any task that was disabled or not live, so when a bad release held back every task for about 10 hours the tick stamp advanced over the due occurrences, no `task_runs` row showed the gap, the restart catch-up had nothing to replay and the only trace was one audit row per process. Now (`src/web/schedule-skip-ledger.ts`): every due occurrence of a task that is enabled but held by the review gate (`draft`/`pending_review`) is recorded per target agent as a `skipped_not_live` run, and a task that is part of a mass disable (a majority of the tasks that were runnable a tick earlier are all switched off at once, at least 4 tasks in play) is recorded as `skipped_disabled` for as long as it stays off, at most 24 h. One deduped alert (audit row `mass_skip`, Telegram when configured) goes out when such a mass event starts and re-arms once it is over. A task the operator disabled on its own, a single toggle, and tasks that were already disabled before the event leave no rows and are never replayed by a catch-up. The scheduler also reconciles `task-config.json` `enabled` from the DB at startup and hourly (file <- DB only, just that key is rewritten, a missing or unparseable file is left alone); the mirror had drifted to `enabled=false` on 17 files while the DB said enabled. The detection also survives a restart: a fresh tracker used to start with an empty "runnable a tick ago" history, so a process that came up already inside a mass event (every task reading as disabled from its first tick, the DB still enabled) took that state as normal and recorded nothing, with no alert. The first scan now seeds that baseline from the DB rows themselves (enabled and live, via `listDbRunnableTaskNames()`), so the held occurrences are recorded as `skipped_disabled` and the alert goes out from the first tick; tasks the DB has disabled are not in the baseline and still leave no rows, a failing baseline read falls back to the tick's own evidence.
