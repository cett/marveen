### Added

- Sidebar: the Tasks entry shows a badge with the number of scheduled tasks the review gate holds (`pending_review`), hidden at zero, like the Updates and Approvals badges. A task a non-admin changed (or a prompt rewritten through the API) stops running until an admin activates it, and nothing in the sidebar said so. The count comes from the unfiltered list (a tenant filter on the page does not change it), is polled at load and every 5 minutes, and is refreshed after every list load, so it drops right after an activation.
- `scripts/recipe-wrapper-dry-run.ts` also scans the main agent's own skills (`<install>/.claude/skills`, owner `main`), next to the global and per-agent skills, the CLAUDE.md files and the scheduled tasks. It stays read-only: it lists the old curl recipes that would move onto `scripts/agent-api.sh`, with the admin-only calls marked.
- **[API]** Token shadow counter (Phase T2, migration 0079, `token_usage_shadow`). Measures how the shared dashboard token and the per-agent tokens are used before any rule is enforced on them. It only counts: nothing is allowed, refused or delayed because of it, and a counter fault (a missing table, a failed row-owner lookup, a throwing body observer) never reaches the request. The numbers are an aggregate, one row per UTC day, category, method, route template (ids, agent names and schedule names become `:id` / `:agent` / `:name`), caller, caller source (`token`, `self_declared` or `none`), client bucket and target, with a counter and the last timestamp, so the table grows with the number of distinct shapes, not with traffic: shapes beyond 4000 a day fold into one overflow row, rows older than 90 days are pruned by the writer, and a caller or target that is not a plain agent id is stored as `_invalid`. Categories: `shared_token_use` (every request on the shared dashboard token, which resolves as the admin token named `dashboard` once enrolled, or as the bare file token before; the caller being its `X-Agent-Id`, marked a self-declaration; the main agent's and the operator's named tokens are not the shared token); `agent_id_mismatch` (a caller that is an agent and not the main agent names another agent on an endpoint that takes an agent id: the conversation ledger first, then agent state and task state, daily log, spans, hook audit, tool log, skill usage, artifacts, approvals and the sender of a message; the path, the query and the body, a batch included, are read); `foreign_row_access` (the same for memories, workspace documents, kanban, the blackboard and schedules, where a fleet agent token is held by permission only: the agent a request names, or the owner of the row it addresses, is not the caller); `unscoped_read` (a memories or workspace listing with no agent filter); `missing_tenant_context` (a shared agent with no fresh tenant context: a fleet token refused with 403, or a shared-token request that declares such an agent and names no `?tenant=`); `shared_agent_memories_no_tenant` (`GET /api/memories?agent=<shared agent>` with no tenant); `fleet_skill_write_denied` (a fleet agent token's skill write that the skills route refuses). The server cannot see the calling process, so the row carries a coarse User-Agent bucket (`curl`, `python`, `node`, `browser`, `other`, `none`) in its place. A tenant-less answer for an agent is cached for 5 seconds, so a context that just appeared can still be counted for that long. `GET /api/token-shadow` (admin only; `?days=1..90` default 7, `?category=`, `?caller=`, `?route=` a literal substring, `?limit=1..1000` default 200) returns the totals per category and the rows; the read itself is never counted. Security level: nothing is weakened or newly allowed; the endpoint is `admin:all`, so no fleet agent token or tenant user reaches it, and the counter stores agent ids and route templates, never a token, a request body or a query value.
- **[API]** Per-agent API tokens (migration 0078). `api_tokens` gains a nullable `agent_id` and the role CHECK learns `fleet_agent`: a token that names the agent it belongs to, so the server no longer takes an agent's identity from the self-reported `X-Agent-Id` header. A `fleet_agent` token carries no tenant: the tenant of a request is the one the agent serves right now (its fresh tenant context, or its single tenant), and a shared agent with no fresh context is refused with 403. `POST /api/admin/tokens` accepts `agent_id` (required for `fleet_agent`, a label on an `admin` token such as the main agent's own named, revocable token); rotation keeps the agent. The role holds the plumbing an agent needs to run itself (new permissions `ledger:*`, `agent-state:*`, `daily-log:*`, `telemetry:write`, `artifacts:*`, `skills:*`, `fleet-config:read`, held by `admin` and `fleet_agent` only) plus the memory, kanban, message, approval request, blackboard and schedule permissions of a tenant agent; it never holds `admin:all`, `agents:write` or federation.
- **[API]** A `fleet_agent` token acts only as its own agent: `/api/conversation-ledger*` (path and every entry of a batch, all or nothing), `/api/agent-state`, `/api/agent-taskstate`, `/api/daily-log`, `/api/spans`, `/api/hook-audit`, `/api/tool-log`, `/api/skill-usage` and `/api/artifacts` refuse another agent's id with 403; the sender of `POST /api/messages` is the token's agent (an omitted `from` is filled in, a different one is a 403); `POST /api/approvals` asks as the token's agent and `GET /api/approvals` lists only its own requests, while the resolving `PATCH` is a 403; `PUT`/`DELETE /api/skills/sql/:id` accept only `agent/<own agent>/...`. The admin tokens and the shared dashboard token are unchanged. Memories, workspace documents, kanban and the blackboard are reachable by permission only for now; their per-agent scoping follows.
- `npm run agent-tokens`: issues, rotates and revokes the per-agent token files (`agents/<name>/.agent-token`, mode 0600; the main agent's and the operator's named admin tokens next to them). A new agent gets its token at creation, a deleted agent loses its tokens, and a generated agent CLAUDE.md reads the agent's own token file once it has one. Nothing prints a token; the files are what the consumers read.
- **[API]** `conversation_log.tenant_id` (migration 0075, nullable). The backfill marks the rows of an agent served by two or more tenants `_multi_` and every other row `default`; a new turn is stamped by the server from the channel binding of its chat (Telegram), and a chat without a binding stays NULL (unknown), not `default`. The tenant purge removes a deleted tenant's turns.
- **[API]** Internal endpoints that replace direct database access in scripts and hooks (preparation for the PostgreSQL move; all admin-only, unmapped in the RBAC table): `GET`/`PUT /api/agent-state/:agent/:key` (a closed key set: the blackboard-hygiene sweep state and the kanban-audit timestamp), `/api/intel/{init,dump,facts,watchlist,focus,decisions}` (the intel registry, still its own `store/intel.db`, now opened only by the dashboard), `GET /api/admin/tenant-gate-status` (applied gate migrations, tenant context rows, multi-tenant agents without a channel binding), `POST /api/conversation-ledger` with `GET /api/conversation-ledger/:agent/recent` and `.../open-question` (the channel-turn ledger behind the continuity hooks; a write takes one turn or a batch and is idempotent), and `POST /api/skill-sync` (the database half of the SKILL.md write-back hook; it does not regenerate the file the agent just wrote).
- `scripts/non-ts-db-access-ratchet.py`, run in CI: the Python, shell and skill-text code outside `src/` that opens the database file directly may not grow, and every such file carries a disposition (stays on the database, moves to the API, operational tooling, not our database). `--report` shows how much is left.
- **[API]** Skill usage is now captured beyond the `Skill` tool. `skill_usage` gains a nullable `source` column (migration 0070, no backfill; `trigger_type` and its CHECK are unchanged, so the dream-engine query and the Skills page counters keep working): `skill_tool`, `read_tool`, `bash_read`, `bash_script` or `api_read` or `slash`. The `skill-usage-capture` PostToolUse hook, whose matcher is now `Skill|Read|Bash`, also logs a Read of any file inside a skill directory (not only `SKILL.md`) under the global, project-level, agent-local and `.claude-config` skill roots; a Bash `cat`/`head`/`tail`/`sed -n`/`less`/`more`/`bat`/`nl`/`awk`/`grep`/`rg` of a concrete skill file; a Bash interpreter or `./` run of a skill's `scripts/` file; and a Bash `curl` GET of `/api/skills/sql/<id>` or its `/files`. These do not count: `ls`, `stat`, `wc`, `cp`, `mv`, `rm`, `rsync`, `tar`, `git`, `sed -i`, `tee`, redirections, quoted text and heredoc bodies, a curl with a non-GET method or a body, the skills-API list, and anything that names the skills root, a glob or a variable instead of one skill. It is best effort: a path built at runtime, a command inside `bash -c "..."` and a path with a space in Bash commands are not seen. `POST /api/skill-usage` accepts an optional `source` (400 `invalid_value` on an unknown value or one that disagrees with `trigger_type`; a request without it, from an older hook, stays valid) and `GET /api/skill-usage` returns it, derived from `trigger_type` for older rows. The hook never holds a tool call up: all the posts of one run share a 1.2 second budget (a hung dashboard costs it once, the rows are simply not written), and `awk -i` (in-place or include) does not count as a read. A repeat of the same agent, skill, session and source within 60 seconds is recorded once, so a script run in a loop does not inflate the 30-day counter. A startup migration (`ensureSkillUsageMatcher`) widens an existing sub-agent's `Skill|Read` matcher to `Skill|Read|Bash` without duplicating the entry or widening other hooks that share it; a running session picks the new matcher up at its next restart. The same hook also runs on `UserPromptSubmit` (seeded into existing sub-agents by the regular hook backfill) and logs a prompt that starts with `/<name>` as `source=slash` (`trigger_type` `tool_call`) when `<name>` is an existing skill directory (global, project-level, agent-local or config alias); built-in commands (`/clear`, `/help`, `/rename` and the rest, even if a skill directory shares the name), unknown names, plugin-qualified names, paths and a prompt that does not start with the slash do not count. Since there is no backfill, a skill counted only from Bash or a slash call shows no history before the deploy
- Blackboard: a `blocked` row no longer sticks forever. `POST /api/messages` with `complete: true` now closes the sender's `blocked` row to `done` as well as `assigned` and `active` (a `stale`, `done` or missing row stays a no-op); `scripts/blackboard-hygiene.py` nudges an idle running agent whose `blocked` row is older than one hour (own nudge text, the same two-round counter and `[ESZKALACIO]` escalation to the coordinator, at most one message per agent per round); the agent template's Fleet Blackboard section tells an agent to set a finished block to `done` (nothing clears a `blocked` row automatically) and to message the main agent when a block needs someone else (restart, auth, a decision). Cause: a blocked row stayed after a successful re-run. README: the vault-file-materializer paragraph names the syncback trap (a manual token refresh is overwritten when the running MCP stops and writes the old file back to the vault; right order: replace the running temp file, then `vault-set`, then restart)
- The outgoing-copy gate runs the mixed-script (homoglyph) check on inter-agent `curl .../api/messages` calls, and `scripts/agent-msg.sh` runs the same shared rule (`scripts/lib/mixed_script.py`) before it sends: a Cyrillic or Greek look-alike inside a Latin word blocks (gate exit 2, helper exit 3), a checker that cannot load blocks, and the micro sign, superscripts and subscripts (`40 µs`, `H₂O`) pass on every path including email and Telegram. An inter-agent body the gate cannot interpret passes with a system message, and a missing checker file only warns; both are deliberate and called out in the code. The hook also gained a `__main__` fail-closed net (a crash exits 2)
- **[API]** Homoglyph warning on the durable write paths. `POST /api/memories`, `POST /api/daily-log` and `POST /api/messages` still save the text unchanged, but when it carries a Cyrillic or Greek look-alike letter the 200 response gains a `homoglyph_warning` field that cites codepoints, never the raw letter. Warn only, never block or rewrite: vendored text, real foreign-language records and technical Greek notation are legitimate
- **[API]** Kanban homoglyph journal. Two insert triggers on `kanban_cards` and `kanban_comments` (migration 0069) record rows whose text carries one of the measured look-alike letters in `homoglyph_findings`, so writes made with sqlite3 directly are seen too. `GET /api/homoglyphs` lists unresolved findings (`?all=1` includes resolved ones) and `POST /api/homoglyphs/:id/resolve` marks one read. Admin only, because a finding carries a sample of the row text
- **[API]** `POST /api/messages` rejects a local recipient that is not a registered agent with 400 at once (`field: to`). A placeholder recipient used to get 200 and only turn `failed` after the retry window, so the sender believed it was delivered. A registered agent that is merely not running keeps the retry path, and `<system>/<agent>` federation addresses are unchanged
- `scripts/hooks/bash-egress-parser.mjs`: a Bash PreToolUse hook on every sub-agent that parses the command and denies an external destination while localhost and the local network always pass. It reads the argv of curl, wget, aria2c, axel, lynx, w3m, links, elinks, httpie (`http`, `https`), xh, ftp, sftp, tftp, telnet, nc/ncat/netcat, socat and `openssl s_client`, skipping each tool's value-taking flags (`wget -O out.txt http://localhost:3420/x` passes, `wget -qO- example.org/x` is denied); interpreter one-liners with a network primitive; one-liners that spawn a process (the curl or wget command line or argv list inside `subprocess`, `os.system`, `execSync`, backticks is read, and a list whose host is not a literal is denied, while a localhost curl that only carries an external URL as data still passes); `osascript` `do shell script`; gawk `/inet/`; and bash `/dev/tcp` and `/dev/udp`. It sees through `bash -c`, `sh -c`, `eval`, subshells, groups, a single `&`, quoted or escaped command words (`c"ur"l`, `\curl`) and wrappers with their flags (env, sudo, timeout, nice, stdbuf, xargs and others); an alias or function defined in the same command line (`alias c=curl; c https://x`, `c(){ curl "$@"; }; c https://x`) is judged as what a call to it expands to, `command` and `builtin` are seen through, a command name held in a variable assigned in the line is expanded, a function body may also be a subshell or a compound command (`c() ( curl "$@" )`, `c() if ...; fi`), `${VAR:-default}` and `${VAR-default}` stand in with the default when nothing assigned VAR, and a command word that stays unresolved (`$CMD`, `$(...)`, any `$` left after expansion except a plain `$HOME/` path with no variable or substitution after the prefix) next to an external-looking URL or host is denied (an alias or function from an earlier tool call or a sourced file stays open, as do runtime-built names); `env -S`, `watch`, `su -c`, `runuser -c`, `script -c`, `flock -c` and `sudo -i/-s` hand a command line to a shell or split it, and that line is read as a command of its own; an xargs-fed client with no literal destination is denied. A command it cannot parse (unterminated quote or heredoc) is now denied when it carries anything network-capable, where it used to pass. Still open, and said so in the hook header: calls inside script files and heredoc-fed interpreters, URLs or command names built at runtime, other stdin-fed clients, find -exec, parallel and ssh host commands, and git, pip, npm, ssh, scp, rsync and dig, which are everyday tools and deliberately not denied. Per-install vendor hosts and an opt-in `domains` suffix list live in `store/egress-vendor-hosts.json` (template in `templates/`), private-network targets pass by their literal spelling. Differs from the upstream hook in two ways: it fails closed on an unreadable payload or an internal error, and it keeps its block log and vendor list under `MARVEEN_STORE_DIR`. The main agent is not covered
- Sub-agents can no longer edit the files that bind them. The self-pace gate refuses the native file tools (by resolved real path, so relative paths and symlinks are followed) and allows only plain reads and plain runs in Bash for: `store/egress-allowlist.json`, `store/egress-vendor-hosts.json` (it would let a sub-agent whitelist any host for the egress parser), `store/.egress-allowlist-cache.json` and the history directories of the first two; and the gate and hook executables of this install: `scripts/self-pace-gate.mjs`, `scripts/email-send-gate.mjs`, everything under `scripts/hooks/` and `scripts/lib/`. The protected set is the real paths under the install the gate runs from, not a name pattern, so a git worktree copy stays editable and `node scripts/hooks/x.mjs`, `python3 scripts/hooks/x.py`, `git add` and `cat` keep working in the install itself. Bash is fail-closed: the command is split quote-aware, each word is resolved against the payload cwd and every `cd` in the command (after `~`, assigned variables, brace expansion and globs), and cp, mv, tee, sed -i, rm, an interpreter with inline code, a command substitution next to the path, or any redirect (`>`, `>>`, `>|`, `&>`, `>&file`, `N>&file`, `<>`) naming a protected path is denied; a read piped into a non-reader is denied too. The "plain read" is judged per command, not by name: `sort -o`, `uniq IN OUT`, `xxd IN OUT`, a `sed` script with a `w`, `e` or `r` command (any sed script outside a print/delete/quit/`s///` shape, and `-f`), `file -C`, `rg --pre` and `find -fprint` are not reads, pagers are not listed, and `git` read subcommands are refused with `--output` (or an abbreviation), `-c`, `--config-env`, `grep -O` or a `GIT_*` / `PAGER` / `LD_PRELOAD` / `PATH` assignment in front. A `cp` into a directory is judged by the file it would create there (`cp /tmp/settings.json agents/<name>/.claude/`, `cp -t DIR SRC`), a source name that cannot be read counts as the protected name; every protected path compares without regard to case; a recursive `cp` is judged by the tree it would create or merge into; `agents/` and `agents/<name>` are refused only when the operation can put a settings file in or take the directory away (`mkdir`, a copy, rsync, ditto, mv or `tar -x` of a source, or an archive listed with `tar -tf`, that carries no `.claude` or `.claude-config` settings file and no symlink stays allowed, a source that carries one or cannot be read is refused, and so are `rm`, `ln`, moving the directory away and a copy named like a config directory); `env -S` and `--split-string` are split and the command inside is judged like any other. A directory that holds protected files (`scripts/`, the store directories, the install root) can be listed, read and entered, but moving, removing, re-linking, extracting into or rewriting it is denied (`scripts/` for any non-read, the others for those commands). The sub-agent's own Claude Code settings are protected the same way (owner decision): `agents/<name>/.claude/settings.json` and `settings.local.json`, the same two under `agents/<name>/.claude-config/` (the config directory of an isolated agent), and the install's `.claude/settings.json` and `settings.local.json`, matched by real path under this install's `agents/` directory (an agent or file that does not exist yet included), with the `.claude` and `.claude-config` directories themselves protected against being moved, removed or re-linked; a `settings.local.json` with `{"disableAllHooks": true}` would otherwise switch every gate off. Reads (`cat`, `jq`, `grep`) stay allowed, a worktree copy stays editable, and changes to settings are made by the main agent or the owner; the deny message says so. Not covered, on purpose: the user-global `~/.claude/settings.json`. Limit: a script that builds the path at runtime is not seen. Other files in `scripts/` are not protected. For the two store config files the dashboard keeps a sha256 baseline with a full copy of every version under `store/egress-allowlist.history/` and `store/egress-vendor-hosts.history/` and queues a system message to the main agent with the diff, so a change by any route is recorded and recoverable; the script files have no baseline (they change on every deploy; `git status` shows an edit). `egress-gate.mjs` now ignores a runtime cache stamped in the future. `MultiEdit` is now in the gate's matcher, and a wired gate with the older matcher is widened at startup
- **[API]** Vault read audit and SSH private-key refusal. `GET /api/vault/:id` writes one structured log row before it answers, for a found secret, a missing one and one the caller's tenant may not read alike: the id, the credential kind, the principal name (a session user, a device, a federation peer, a registered token's label, or `token` for the legacy file token), the verdict of the new read-only allowlist `store/vault-acl.json` (`{ "<secret-id>": ["agent-id", ...] }`: `owner-lane`, `allowed`, `not-listed` or `no-acl`), `mode: audit` and `found`. The value is never passed to the logger. Audit only: nothing is blocked and no secret is narrowed, a missing or malformed allowlist file counts as empty with a warning. The allowlist is not a secret and lives outside `vault.json`, so the dashboard can read it without the master key. Separately, an SSH private key (`ssh-key-<id>`) is no longer handed out by the generic routes: `GET /api/vault/ssh-key-<id>` answers 403 `forbidden` without decrypting it (the audit row stays), `POST /api/vault/bindings` refuses such an id with 400 `invalid_value` and logs `vault-binding-refused` (id, principal, never a value), and `scripts/vault-resolve.mjs` (exit 4), `scripts/vault-materialize.mjs get` (exit 4) and `scripts/vault-inject-http-mcp.mjs` (config left untouched) refuse it as a second layer, since a header or env binding would send the key to a remote server or a child process. The SSH feature itself reads its keys in-process and is unchanged
- A fleet-wide deny floor on every security profile. `permissions.deny` is rebuilt wholesale from the profile on every spawn, so a rule that one profile carries (or that is written by hand into a `settings.json`) is gone at the next respawn and a lean profile never had it. `FLEET_BASELINE_DENY` (`src/web/agent-scaffold-hooks.ts`) is now added to every sub-agent's deny list in `writeAgentSettingsFromProfile` (deduped against the profile's own rules): `Read` of `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.env` and `**/.env`, `sudo` with its `*/sudo` partner, `rm -rf` of the home directory and of `/`, `git push --force` and `-f`, and the unsafe browser-code MCP tool. The main agent gets the same rules from the tracked `.claude/settings.json` (a test keeps the file and the constant identical). It takes effect at the next spawn, there is no startup migration. Two groups of rules are stated in the source as weaker than they look: the force-push rules are friction (an inserted flag or an absolute path walks past them), and the narrow `rm` rules have no absolute-path partner. The broad `rm` ban, `*/git *` and `curl -X POST` (a weak guard that `curl -s -X POST` walks past, and it would deny the fleet's own localhost dashboard recipes; owner decision) are left out on purpose. A profile may still carry the broad `rm` rule itself (marketer does)
- Per-agent tool deny that survives a respawn. `agent-config.json` takes an optional `toolDeny` list of bare tool names (`Artifact`, `Workflow`, `mcp__server__tool`), merged into the agent's `permissions.deny` last on every spawn. A whole-tool-name deny also drops the tool's schema from the prompt, which makes it a context handle, but a name written straight into `settings.json` used to vanish at the next respawn. Only bare names are accepted (a `Tool(pattern)` rule or free text is dropped, at most 64 entries), so the field can only widen the deny list and removing it takes the names out again at the next spawn
- **[API]** `GET /api/marveen` and `GET /api/settings` are readable by every signed-in role (`memories:read` in the endpoint table), because every dashboard session calls both at boot (brand and agent name, the UI language) and enforce mode would otherwise refuse them for a non-admin. The admin, and the legacy bearer token, still get the full response; any other role (and a request with no resolved role) gets an allowlist: `name`, `brandName`, `agentId`, `role`, `channelProvider` and the kanban display config from `/api/marveen` (no instruction files, MCP config, owner name, description, model, session or channel details), and only `DASHBOARD_LANG` with `key`, `type`, `value` and `default` from `/api/settings` (the filter runs before any value is read, so secret and unlisted settings are never resolved for them). A field added to either response later stays admin-only until it is put on the allowlist (`src/web/non-admin-views.ts`). `PUT /api/marveen` and `POST /api/settings` stay `admin:all`. For a non-admin the main-agent card of the Agents page shows `-` for the fields it no longer receives. Security level: not lowered for any existing caller (the roles that could read these before were admin only in enforce mode, and in shadow mode everything was readable by everyone); the new read access is limited to the allowlist.
- Agents shared by several tenants never get a file copy of a tenant skill: their tenant skills are DB-only. `TENANT_SKILL_FILES=single` (the default) already skipped them, but the `all` value wrote the copy (and its companion scripts) to shared agents too; it is removed and read as `single`, with a startup warning. An availability change (`PUT /api/admin/agent-availability`) used to reconcile only the changed tenant's skills, so enabling a second tenant on a single-tenant agent left the first tenant's generated copy on what had become a shared agent until the agent's next stop; it now reconciles every tenant the agent serves (the copy goes when the agent becomes shared, the remaining tenant's copies are written when it becomes single-tenant again; a hand-edited `SKILL.md` is kept, the generated companion files go). The fork guide (HU+EN, F02) documents the rule and the owner's accepted risk (a shared agent still reads any tenant's skill rows through the API with the fleet token; the use-time gate covers the `Skill` tool and file access, not a `curl` from a shell), and the MCP chapter (F06) documents why there is no tenant filter at the MCP layer today (no Marveen-hosted MCP server; the catalog servers are external and have no `tenant_id`), what protects a tenant instead, and that tenant filtering is mandatory if a Marveen-hosted MCP server is ever built.
- Role-based nav gating for the dashboard. A role that cannot be served by the API no longer sees, or lands on, the page: Messages, Skills, Ideas, Artifacts, Token monitor, Updates, Settings, Backups, MCP connectors and Import (all `admin:all`), and Federation (`federation:read`, so `read_only` and `viewer` lose it, `agent` keeps it) are hidden for them in the sidebar, a sidebar group left empty collapses, and a typed hash, a bookmark or an in-app link to such a page (including the `#migrate` alias) lands on the overview. Inside open pages, the background-tasks tab of Tasks (`#bgTasks` falls back to the scheduled tab) and the Claude-status block of the overview are hidden and their calls skipped. The Tasks page itself stays open: its permissions (`schedules:read`) are granted to every role. The gating is `data-rbac-perm` attributes in `index.html` plus one router guard (`web/modules/nav-gate.js`, `can()`/`roleHas()` from `rbac-client.js`); it never unhides what other code hides, and a caller with no session role (the legacy bearer token) sees everything as before. It is a UX layer only: the server's 403 stays the last word and nothing on the server changed. The boot-time and background calls that every session used to make to `admin:all` endpoints (the 5-minute updates badge poll, onboarding status, the connector install banner, network info, the model list, the federation status for roles without it) are skipped for a role without the permission, because each of them would otherwise be refused in enforce mode and would write a would-deny row to the RBAC shadow log on every page load. A test walks every gated page's load calls against the real endpoint permission table (a page is hidden for a role exactly when the server would refuse it, never more), the screen-access matrix of the Users tab now shows those cells as `none` instead of `gap`, and a Playwright smoke covers viewer and admin. Still refused for a non-admin session in enforce mode and not changed here: `GET /api/marveen` (brand and agent names, called at boot) and `GET /api/settings` (the language preference), which need a policy decision before enforce.

### Infrastructure

- Recall/quality baseline harness for the PostgreSQL migration (`scripts/eval/`, with a README). It freezes what the current retrieval pipeline returns for a fixed query set so a later backend (tsvector + pgvector) can be compared against it: `prepare` copies the live database into an isolated eval directory with the SQLite backup API (the source is opened read-only, and every later step refuses to run against anything that is not such a copy), `gen-queries` derives a seeded, reproducible query set from the corpus, `embed` caches the query embeddings once so a snapshot needs no network, `snapshot` runs the real pipeline with a frozen clock and writes the ordered ids per stage, and `compare` checks a candidate snapshot against a baseline with the accepted thresholds (recall@10 >= 0.99, top-5 overlap >= 0.95, nDCG@10 drop <= 0.01) and exits 1 on failure. A snapshot is bit-identical across runs, with the reranker on and off; the reranker moves the top 5 a lot (overlap 0.54 against the plain rank fusion), so two baselines are kept and a PostgreSQL candidate is compared against the reranker-off one. The real query set, the embedding cache and the baselines carry private memory content and live under the gitignored `store/eval/`; only the harness and synthetic unit tests (32, the sqlite-vec ones skip themselves when the extension is missing) are in the repository
- `INSERT OR REPLACE` on `sessions` (`setSession`) and `token_usage_cursors` (the token-usage scan) is now an explicit `INSERT ... ON CONFLICT(key) DO UPDATE SET` of every other column. `OR REPLACE` deletes the old row and inserts a new one, which would fire a delete trigger or an `ON DELETE CASCADE` on a referencing table; neither table has one, and every column is written, so the stored result is the same. The third use, on the sqlite-vec `vec_artifacts` virtual table, stays (vec0 has no upsert) until the pgvector phase. Ratchet baseline `INSERT OR REPLACE` 3 -> 1
- 13 of the 14 `instr()` calls are gone (the ratchet baseline is now 1). The start-up fold that lowercases the system prefix of federation ids in `agent_messages.from_agent` / `to_agent` now selects the few rows that contain a `/` and folds them in code (same result: only the prefix before the first `/` is lowercased, the agent segment keeps its case, and a second pass changes nothing). `failPendingFederatedMessages` scopes to one peer with an escaped `LIKE '<peer>/%'` on `lower(to_agent)` instead of `instr`/`substr` (a `_` in a peer id is still a literal, case still does not matter). - Phase T3, the consumers move to the agents' own tokens. Every hook, gate, operator script, template, seeded task, shipped skill and generated agent instruction block that called the dashboard API with the shared dashboard token now goes through `scripts/agent-api.sh`, which signs with the calling agent's own token (`agents/<name>/.agent-token`, the main agent's in the install root, the operator's `store/.operator-token`) and hands it to curl on stdin, so no token is read into a command line, a generated CLAUDE.md or a transcript. The shared token stays as an explicit, visible fallback only when the own token file is missing (the request then carries `X-Agent-Id`, so `GET /api/token-shadow` shows who fell back); a present but refused token is never retried on the shared one. Nothing is enforced yet, so every call that worked before still works. The calls an agent token is refused on (agent start/stop/restart, vault, egress allowlist writes, global skill writes, `/api/voice/tts`, the `/api/v1/admin/*` routes) use `--token admin` (the main agent's own admin token, the shared one for every other agent) until enforcement is decided.
