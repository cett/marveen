Logging-category hook (fail/timeout -> silent pass, never blocks a tool call); no network calls, local SQLite reads only. - **[API]** fix the Vault (encrypted secret store + SSH key pool) having no tenant concept at all, and a security hole in the fix: a shared single-key store meant a tenant-scoped caller could shadow or overwrite a fleet-level secret (or another tenant's) that happened to share the same id. `vault.json` entries and the `vault_ssh_keys` table now carry `tenant_id`, and every store operation (`setSecret`/`getSecret`/`deleteSecret`) keys off the compound `(tenant_id, id)` pair rather than `id` alone -- existing entries backfill to `default` on read, and every internal caller (agent API-key storage, MCP binding sync, env resolution) keeps calling these without a tenant argument, which resolves to `default` and only ever touches fleet-level secrets. `GET/POST /api/vault`, `GET/DELETE /api/vault/:id` and the whole `/api/vault/ssh-keys` sub-tree now scope by tenant the same way the existing tenant-isolated routes do (admin with no `?tenant=` sees everything, admin with `?tenant=` narrows, non-admin is always scoped to their own tenant), with cross-tenant single-item access returning 404 rather than 403 (anti-enumeration, so a scoped caller can't use the response to confirm a given secret id exists under another tenant)
- fix 3 npm audit findings (`qs` moderate ReDoS, `adm-zip` high, `xlsx` high) reported against transitive/direct dependencies -- `qs` and `adm-zip` are pinned via `package.json` overrides to their patched versions (both are pulled in transitively, by `express`/`body-parser` and by `onnxruntime-node` respectively; neither is used directly by application code), and the `xlsx` package is replaced entirely with `exceljs` for the local `.xlsx`/`.xls` file-import worker (the only consumer). Migrating to `exceljs` pulled in a moderate `uuid` advisory as a new transitive dependency, also pinned via override. Behavior for `.xlsx` import is unchanged (same columns/rows extracted); legacy binary `.xls` files (pre-2007 format) are no longer parseable, since `exceljs` only reads the OOXML zip container -- such files now fail with a clear `corrupt_workbook` error instead of silently mis-parsing
- **[API]** fix Import Sources (file/Google Drive/SharePoint document ingestion) having no tenant concept at all -- `import_sources` and `import_audit_log` had no `tenant_id` column, so `GET /api/import/sources`, the per-run log, `/api/import/stats` and `/api/import/search` returned every tenant's configured sources and ingested content to any authenticated caller, and a tenant-scoped user could edit, delete, re-sync or wipe another tenant's source outright. Migration adds `tenant_id` to both tables (existing rows backfill to `default`, approved; audit-log rows inherit their tenant from the parent source); the list/log/stats/search endpoints now scope by tenant the same way the existing tenant-isolated routes do (admin with no `?tenant=` sees everything, admin with `?tenant=` narrows, non-admin is always scoped to their own tenant), the per-source endpoints (`PUT`/`DELETE /api/import/sources/:id`, `POST .../sync`, `GET .../log`, `DELETE .../memories`) 403 a non-admin acting on a source outside their tenant, and the crawler now stamps the owning source's `tenant_id` on every `import_memories` row and its shadow memory. The fleet-wide `DELETE /api/import/memories` wipe stays admin-only
- **[API]** fix the Memories page stat cards (total/byTier/vectors/import counts) ignoring the tenant selector, unlike the list below them which already filtered correctly -- the tenant-selector callback only re-ran `loadMemories()`, never `loadMemStats()`, and even when `loadMemStats()` did run it never forwarded the selected tenant to `/api/memories/stats` or `/api/overview`. `getMemoryStats()` in `src/db.ts` now takes an optional `tenantId` and scopes every underlying query (including `import_memories`, which already carries a `tenant_id` column since migration 0017); the stats route resolves it the same way the existing tenant-scoped endpoints do (admin with no `?tenant=` sees the fleet-wide total, admin with `?tenant=` narrows to it, non-admin is always scoped to their own tenant regardless of the query string)
